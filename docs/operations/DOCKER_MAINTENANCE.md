# Docker: диагностика и очистка

## Что означает подсветка Dockerfile

Проверка от 6 ноября 2026 года воспроизвела сообщения через установленный в VS Code Docker Language Server с включённым сканированием образов. Ошибок синтаксиса в восьми Dockerfile и пяти файлах Compose не обнаружено. Проверка `docker buildx build --check` также прошла для восьми Dockerfile; для межсервисного образа использован доступный локальный образ Commercial как контекст проверки.

Найдены два отдельных источника предупреждений:

- `outdated_digest` — SHA256 в `FROM` больше не соответствует текущему содержимому того же тега в реестре. Обновлены ссылки FrankenPHP в Core и Commercial, а также Go и PostgreSQL в сборке БД. Теги PHP 8.3.36, Go 1.27.3 и PostgreSQL 18.6 сохранены.
- `critical_high_vulnerabilities` — сканер сообщает об уязвимостях пакетов базового образа. Это требует разбора состава и конечного образа. Обновление SHA256 само по себе не устраняет такие находки. Docker CLI для provisioner закреплён версией 29.9.3 и SHA256.

Настройки диагностики IDE и исключения CVE при этой работе не менялись. Теги Compose `!override` и `!reset` зарегистрированы в существующем `.vscode/settings.json`; после загрузки настроек YAML Language Server принимает их без ошибок.

Резервирование и мигратор раньше наследовали обычный `postgres:18`, обходя исправленную сборку проекта. Теперь оба используют `platform-postgres:local`. Compose передаёт его через именованный контекст `postgres-base` и собирает зависимость первым. Настоящая совместная сборка PostgreSQL, резервирования и мигратора прошла. В режиме `--check` BuildKit не смог проверить ссылку на другую цель сборки (`unsupported context source target`), поэтому для этой связи нужна именно настоящая сборка.

Повторное сканирование собранного PostgreSQL через Trivy 0.76.1 с обновлённой базой показало 1 критическую и 66 высоких находок в пакетах Debian; поле исправленной версии отсутствует у всех 67 записей. Для заменённого `gosu` находок нет. Это число записей «пакет — CVE», а не количество уникальных CVE. Образ не объявлен безопасным для выпуска. Порядок работы с остаточным риском: [безопасность образов](IMAGE_SECURITY.md), [готовность выпуска](READINESS.md).

Docker Scout и Trivy могут показывать разные результаты: в локальном отчёте Scout присутствовали обе версии стандартной библиотеки Go, включая старый `gosu` из базового слоя; проверка объединённого образа Trivy и версия бинарного файла проверяются отдельно. Число предупреждений на строке `FROM` нельзя выдавать за результат проверки конечного образа.

## Где находится дневник

Education — модуль основного Core backend со схемой `education`. Отдельный постоянный контейнер дневнику не нужен. Маршруты и интерфейс включаются по [инструкции Education](../architecture/EDUCATION_BACKEND.md); наличие кода или тестового стенда не означает, что модуль включён в рабочем окружении.

`platform-education-qa` был отдельным временным стендом: backend, PostgreSQL, Redis и Mailpit. Backend использовал копию приложения из временной папки, а не рабочую установку. Четыре контейнера, два тестовых тома, образ `platform-education-postgres:qa` и сеть этого стенда удалены. Определения тестов в `compose.ci.yaml` сохранены для CI. У сервисов `postgres-test`, `redis-test`, `backend-test` и `control-postgres-test` теперь `restart: "no"`.

## Откуда берутся тома с длинными числовыми именами

Образ PostgreSQL объявляет `VOLUME /var/lib/postgresql`. Если контейнер не получает явное подключение на этот путь, Docker создаёт анонимный том с именем из шестнадцатеричных символов. В PostgreSQL 18 подключение только `/var/lib/postgresql/data` не заменяет том родительского каталога.

Три отключённых анонимных тома проверены через файловую систему Docker Desktop: все содержали кластеры PostgreSQL 18 с базой `platform_test`. Они удалены. Для `db-migrate`, `db-migrate-test`, `backup-worker` и `provisioner-migrator` каталог `/var/lib/postgresql` теперь подключается через `tmpfs`: служебным клиентам БД постоянный кластер не нужен.

Рабочие тома сохраняются:

| Том | Назначение |
| --- | --- |
| `platform_postgres_data` | База Core и модулей |
| `platform_control_postgres_data` | База Commercial |
| `platform_redis_data` | Данные Redis платформы |
| `mybots_postgres_data` | База отдельного проекта MyBots |

## Как очищать окружение

Сначала сопоставьте объекты с контейнерами, включая остановленные:

```powershell
docker ps -a
docker volume ls
docker system df
docker ps -a --filter volume=ИМЯ_ТОМА
docker volume inspect ИМЯ_ТОМА
```

Отсутствие подключений ещё не доказывает, что данные не нужны. Для удаления используйте точные проверенные имена. `docker volume rm ИМЯ_ТОМА` откажется удалять подключённый том. Общая команда `docker system prune --volumes` для этой установки не используется.

Образы отключённых возможностей резервирования и provisioner после проверки сборки можно удалить локально: Compose пересоберёт их при явном включении соответствующего профиля. Образ PostgreSQL основного проекта нужен постоянной установке. Образы, на которые ссылаются работающие контейнеры, сохраняются независимо от наличия тега: `<none>` само по себе не означает мусор.

Кэш сборки не является томом с данными приложения. При очистке 6 ноября освобождено 4,116 ГБ кэша с сохранением резерва 1 ГБ для повторных сборок.
