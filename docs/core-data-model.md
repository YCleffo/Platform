# Модель данных Platform

Структура определяется миграциями и [PostgreSQL-каталогами](database/README.md).
Все поля, допустимость NULL, значения по умолчанию и реальные внешние ключи описаны в
[справочнике](database/SCHEMA_REFERENCE.md). DBML не заменяет защитные ограничения SQL.

## Пять разных идентичностей

`core.persons` описывает человека. `core.accounts` — учётную запись с отдельным
типом, статусом, учётными данными и сессиями. Для человеческого Account нужен Person; сервисный и системный аккаунты не используют человеческий вход. Контакт Person не становится идентификатором входа автоматически.

`commercial.control_users` — пользователи центрального кабинета со своими
подтверждением почты, сессиями и MFA. `commercial.commercial_accounts` — коммерческие
клиенты; доступ задаётся членством. `core.organizations` — организации внутри
конкретной установки. Соответствие по почте, UUID или имени не подразумевается.

## Владельцы данных

| Владелец | Данные | Граница записи |
| --- | --- | --- |
| Person / Account | Люди, контакты, жизненный цикл аккаунта, настройки | API Core и прикладные сервисы |
| Auth / RBAC | Идентификаторы, учётные данные, проверочные запросы, сессии, ключи доступа, MFA, роли и разрешения | Сценарии аутентификации и проверки разрешений |
| Organization | Организации и членства | Разрешения вместе с областью организации |
| Settings / Module | Реестр модулей, настройки, флаги возможностей | Пространство имён, разрешение и запрет секретов |
| Privacy | Согласия, представительство, запросы субъекта, сроки, запреты уничтожения, хранение, инциденты, уничтожение и доказательства | Оркестраторы и поставщики сведений |
| Audit / Messaging | Аудит, исходящая и входящая очереди | Транзакция бизнес-операции, затем фоновый обработчик |
| PlatformRuntime | Идентичность установки, проверенные документы и состояния обработчиков | Инициализация, подпись, последовательность и планировщик |
| Commercial | Каталог, подписки, использование, счета, платежи, чеки, возвраты, установки и лицензирование | Отдельное Symfony-приложение и БД |
| Education | Назначения преподавателей, группы/ученики, занятия/посещаемость, профиль, сообщения, уведомления и метаданные закрытых файлов | Необязательная схема `education` в БД Core; учётная запись Core, разрешение, членство организации и область преподавателя/владельца |

Карта находится в [покрытии](core-database-coverage.md). Таблица не получает
универсальные операции создания, чтения, изменения и удаления только потому, что она существует в БД.
Формируемое покрытие Core/Runtime не включает Education; для необязательной схемы
публикуются отдельные каталог, DBML и покрытие: [покрытие Education](education-database-coverage.md),
[границы и установка](architecture/EDUCATION_BACKEND.md).

## Неизменяемая история

Опубликованный тариф и его цены и возможности задают исторический договор. Новые
условия создают новую версию. Строки подписок и выпущенных счетов сохраняют неизменяемые снимки; новая версия каталога не пересчитывает старый счёт.
Деньги хранятся в точных минимальных единицах валюты. Повтор подтверждения оплаты, уведомления провайдера, возврата или перезапуска обработчика не создаёт новый финансовый эффект.

PostgreSQL хранит постоянную историю. Redis хранит временное состояние. Потеря
Redis не означает потерю платежа. Commercial не читает БД Core; Core не получает закрытый ключ подписи Commercial. Документ прав связывает установку и коммерческое состояние проверенным контрактом, а не объединением SQL.

[Графики процессов](processes/README.md) показывают регистрацию, письма, аутентификацию/MFA, разрешения, каталог, покупку, смены тарифа, продления, возвраты, подготовку установок, персональные данные и фоновые процессы. Стрелка процесса означает действие, внешний ключ означает связь строк.

Критерии промышленного выпуска описаны в
[условиях выпуска](operations/READINESS.md).
