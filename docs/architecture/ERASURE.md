# Controlled personal data erasure (B4)

An erasure case belongs to a subject Person and may reference an in-progress DSAR erasure request. Planning discovers registered candidates across all registered purposes, groups them by physical resource, evaluates retention and creates one item per resource. No candidate, incomplete purpose coverage, or more than 1,000 candidates stops planning. Items store resource IDs and codes, never copies of personal values. A blocked or unsupported resource remains visible as blocked. If a new candidate appears after planning, execution blocks with `candidate_set_changed`; operators must resolve the case scope before claiming full completion.

Execution runs in batches of at most 100. A case advisory lock serializes workers. Each Core item runs in a transaction, locks the subject and case, recollects applicable candidates, re-evaluates retention, active lawful basis, legal holds and dependencies, verifies policy/action and handler ownership, and then calls the registered handler. The physical Core delete, audit record, destruction evidence and item completion commit together. A failed handler rolls back and leaves a retryable failed item. Repeated execution cannot delete a completed item or create a second evidence row. External module handlers must provide item-ID reconciliation for effects outside this transaction.

Core handlers delete owned PersonContact and AccountSettings records. Core has no generic Person, authentication, consent, legal representation, DSAR, audit, or evidence delete; these are blocked until a resource-specific path is designed. No Core anonymize or pseudonymize handler is registered. A handler result must match its requested action.

When a case comes from a DSAR, the caller must supply an approved deadline and calendar type. Only after execution reaches a terminal complete or partial result does the service write execution evidence, satisfy `erasure_completion`, and transition the request. The execution record holds counts and case ID, not deleted values. A case with blocked or failed items is never marked completed. Operators may retry after resolving a block or failure; a partial DSAR response truthfully reports the state at completion.

The HTTP management routes require `core.privacy.erasure.manage` for create/execute and `core.privacy.read` for read/evidence. The console command is `privacy/erasure/execute --case=<uuid> --executor-account=<uuid> --limit=<1..100>`. All reason, policy and resource type values are machine codes. Do not place PII in reason codes, audit metadata, logs, CLI output, or handler errors.

## Backup and restore contract

Primary database erasure occurs at item execution. Existing immutable backups may retain older copies until their documented expiry; B4 does not operate a backup system or promise immediate removal from those copies. Deployment operations must record backup retention and expiry, prevent ordinary access to restored data, compare restored state with the erasure journal, suppress erased resources, reapply erasure before making the restore available, and verify the reapplication. A restore that cannot complete this reconciliation must remain isolated. Destruction evidence has a separate retention policy and survives primary-data erasure.
