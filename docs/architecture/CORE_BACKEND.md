# Архитектура серверного приложения Core

## Направление зависимостей

Вертикальные срезы Core следуют одному направлению:

```text
Обработчик HTTP -> прикладная команда или сценарий -> интерфейс репозитория
                                                       -> адаптер PostgreSQL -> core.*
```

Обработчик разбирает HTTP-ввод и формирует ответ, но не содержит SQL. Прикладные классы не зависят от Yii DB и синтаксиса PostgreSQL. Приведения типов, перечисления, JSONB, `SKIP LOCKED`, значения UUID по умолчанию и сопоставление строк находятся в `Infrastructure`.

## Намеренно ограниченная граница API

HTTP API включает Person, PersonContact, Account, Role, Permission, аутентификацию и сессии, защищённое управление реестром модулей, системными и модульными настройками и флагами возможностей. Маршруты конфигурации требуют явных разрешений; без аутентификации доступен только отфильтрованный `GET /api/public/config`.

Пространства учётных записей не объединяются: Yii Core Account, Control User и Commercial Account различны; сервисная идентичность отличается от человеческого аккаунта. `account_type=service/system` не разрешает машинный вход через человеческий пароль. Отдельно реализованы хешированные сервисные учётные данные, области полномочий, срок, замена, отзыв и `last_used_at`: [сервисная аутентификация M2M](M2M_SERVICE_AUTHENTICATION.md).

Пароль, Google OIDC, Telegram OIDC и WebAuthn Level 3 доказывают первый фактор, но сами не создают сессию. `AuthenticationFlowService` применяет правила аккаунта и MFA; единственный `SessionIssuer` выдаёт непрозрачные токены доступа и обновления после обязательных факторов. Внешний вход, явная привязка аккаунта и процедуры ключа доступа используют разные назначения одноразовых проверочных запросов.

`must_change_password` блокирует обычную сессию после первого фактора до одноразовой проверки смены пароля. Смена собственного пароля требует текущий пароль и недавнее подтверждение личности, меняет хеш Argon2id и контрольную метку безопасности, отзывает другие сессии, создаёт аудит и обязательное письмо.

Настройки Core версии 2, согласия, уведомления и присутствие описаны в соседних архитектурных документах. Управление несистемными ролями требует `core.rbac.manage`; системные роли и правило последнего супер-администратора защищены отдельно. Модули регистрируют коды своих разрешений собственными миграциями.

Публичное представление Account не включает `security_stamp`, сведения о блокировке/входе, создателе/подтверждающем или учётные данные. API аутентификации не выдаёт хеши токенов, паролей и секреты проверочных запросов. Настройки не служат хранилищем секретов: запрещаются похожие на секреты ключи, включая вложенные JSON-ключи. Публичная конфигурация содержит только `system_settings.is_public = true`, без метаданных БД, настроек модулей или конфигурации флагов.

`core.modules` — контролируемый реестр метаданных и состояния включения. Он не загружает PHP-код из БД и не является механизмом подключаемых программ. Core знает конфигурацию доменных модулей, но не их бизнес-логику. `FeatureFlagService` принимает стабильного субъекта, выбранного вызывающим кодом; для постепенного включения авторизованным пользователям применяется UUID аккаунта. Сервис не извлекает личность из HTTP и не использует IP, User-Agent, почту, телефон, токен сессии или отпечаток устройства для выбора участника включения.

## Валидация и пагинация

Проверка Person/Account соответствует ограничениям БД на перечисления, длины, пустые значения, даты, UUID и допустимость NULL. Неверное тело даёт 422 через `ResponseFactory`; неверный UUID пути отклоняется до SQL. Списки используют ограниченную пагинацию по смещению: `limit` по умолчанию 50, максимум 100; `offset` по умолчанию 0. Возвращаются `items`, `limit`, `offset`, `total`.

## Транзакции и параллельный доступ

- Основные контакты Person заменяются в транзакции; частичный уникальный индекс остаётся окончательной гарантией.
- Для нескольких таблиц допустима транзакция внедрённого Yii `ConnectionInterface`; репозитории участвуют в ней.
- Добавление или обновление настроек и флагов атомарно через PostgreSQL `INSERT ... ON CONFLICT DO UPDATE`; изменение и аудит исполнителя входят в одну транзакцию.
- Жизненный цикл модуля сериализуется блокировкой строки, идемпотентен и не меняет `installed_at`.
- Исходящие события захватываются короткой арендой и `FOR UPDATE SKIP LOCKED`.
- Уникальность входящих событий по `(event_id, consumer)` обеспечивает идемпотентность.
- Записи аудита добавляются без обычного изменения; сервисов обновления/удаления нет.
- Завершение MFA, привязка/отвязка внешней записи, включение/отключение TOTP, замена резервных кодов и почтовое восстановление выполняются транзакционно с аудитом и исходящим уведомлением.
- Ключи доступа сериализованы: проверочный запрос потребляется атомарным сравнением и заменой CAS; аппаратный счётчик защищён условием `sign_count = :expected`. Отзыв ключа и отвязка внешней записи используют `CredentialMutationGuard` с `SELECT ... FOR UPDATE NOWAIT`, сохраняя последний способ входа при конкурентных запросах.

Универсальный репозиторий и собственный менеджер транзакций не вводились. Общий код ограничен пагинацией, UUID и исключением конфликта.

## Очистка устаревших данных

```bash
php yii auth/cleanup
```

Удаляются:

1. Истёкшие, использованные и отменённые проверочные запросы: `expires_at`, `consumed_at`, `cancelled_at` раньше текущего времени минус срок хранения.
2. Использованные и отозванные резервные коды по `used_at` и `revoked_at` с учётом срока.
3. Неподтверждённые подключения TOTP после истечения: `verified_at IS NULL AND setup_expires_at < now()`.

Параметры:

- `AUTH_CHALLENGE_RETENTION_DAYS` — 30 дней по умолчанию.
- `AUTH_RECOVERY_CODE_RETENTION_DAYS` — 30 дней.
- `AUTH_CLEANUP_BATCH_SIZE` — 500 записей.

Удаление идёт порциями:

```sql
WITH candidates AS (SELECT id FROM ... FOR UPDATE SKIP LOCKED LIMIT :batch_size)
DELETE FROM ... USING candidates
WHERE target.id = candidates.id AND target.<predicate>
```

Условие повторно проверяется в DELETE целевой таблицы, исключая удаление данных, ставших активными или подтверждёнными после выборки. Отдельный `backend-scheduler` выполняет `php yii scheduler:run`, включая ограниченную задачу `auth_cleanup`. Планировщик и почтовый обработчик проверяются через `/health/ready` и `php yii ops:status`.
