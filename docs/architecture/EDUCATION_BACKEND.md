# Education: предложение по backend

Статус: **проект решения, не утверждён**. Дата: 5 ноября 2026.
Этот документ готовит отдельное решение, требуемое [roadmap](../roadmap/PLATFORM_ROADMAP.md).
Он не объявляет API реализованным и не разрешает открытие Education routes.

## Предлагаемое решение

Разместить Education отдельным модулем Yii runtime: `App\Education`, вне `App\Core`
и вне Symfony Commercial. Хранить учебные данные в собственной PostgreSQL-схеме
`education`, с отдельными миграциями и явно ограниченными правами runtime-роли.
Core остаётся владельцем Account, Person, Organization и аутентификации.
Education зависит от публичных application-портов Core; Core не зависит от Education.
Регистрация модуля и его HTTP routes выполняется в composition root приложения;
отключённый модуль не регистрирует `/api/education/*`.

Вариант с отдельным сервисом `apps/education` и собственной БД также допустим,
но требует отдельного решения о проверке Core identity, service credentials,
синхронизации профилей и эксплуатации. Сейчас готового Education identity bridge нет.
Предложение с Yii-модулем сохраняет существующую границу identity без нового issuer.

Это не включает перенос учебных сущностей в Core, использование Control User
в качестве Core Account или чтение Commercial-таблиц из Education.

## Владельцы и область доступа

| Данные | Источник истины | Доступ Education |
| --- | --- | --- |
| Account, Person, Organization и активное членство | Core | Через application-порты, без записи во внутренние таблицы |
| Учебный профиль и доменные связи преподавателя/ученика/представителя | Education Profile | Собственные записи в `education`; Core membership сам по себе учебную роль не выдаёт |
| Занятия, участники, расписание, материалы | Education Lessons / Schedule | Организация и доступ к конкретному занятию проверяются сервером |
| Timeline, задания и элементы внимания | Education | Проекции реальных доменных записей, с теми же проверками доступа |
| Прочтение и счётчик учебных уведомлений | Education Notification | Собственный inbox; Core notification policy используется для доставки |
| Переписка | Требует решения о Chat | Нельзя выдавать Core email/outbox за пользовательский messenger |
| Avatar | Требует решения о хранении файлов | Только реальная ссылка профиля; отсутствие файла передаётся как `null` |

Каждый запрос разрешается для текущего Core Account, выбранной активной организации
и допустимой доменной связи. Чужие UUID, чужая организация и завершённое членство
не дают доступ. Client query и глобальный список Core Person не задают область доступа.
Учебные permissions регистрирует миграция Education. Privacy export, correction,
retention/erasure и legal holds подключаются через существующие contributor-контракты.

## Предлагаемый HTTP-контракт

Все пути ниже — проект. До реализации и тестов они отсутствуют в runtime и в списке
фактически поддерживаемых OpenAPI операций. После принятия решения создаётся
отдельный Education OpenAPI, согласованный с текущим форматом ответов Core.

| Метод и путь | Данные и правила |
| --- | --- |
| `GET /api/education/today/header` | Реальный display name, nullable avatar, locale, IANA timezone, локальная дата и unread count текущего пользователя |
| `GET /api/education/schedule?from=…&to=…` | Диапазон локальных дат, timezone и реальные занятия; первая версия ограничивает запрос 31 днём |
| `GET /api/education/lessons/next` | Ближайшее доступное занятие либо `null`; завершённые и отменённые занятия не подменяют следующее |
| `GET /api/education/lessons/:id` | Детали существующего доступного занятия для действия «Открыть» |
| `GET /api/education/lessons/:id/participants` | Разрешённый текущему пользователю список участников для действия «Список» |
| `GET /api/education/lessons/:id/materials` | Реальные материалы; чтение метаданных и скачивание проверяют доступ отдельно |
| `GET /api/education/timeline?date=…` | События выбранной локальной даты, порядок по instant и стабильному ID; отсутствие событий — `items: []` |
| `GET /api/education/attention` | Только актуальные элементы внимания текущего пользователя; `items: []` скрывает блок |

Время событий хранится как instant с timezone в контексте расписания. Граница дня
считается сервером в выбранной IANA timezone, включая DST; неделя и выбранный день
не определяются по UTC-дате браузера. Ошибка backend не превращается в пустой день.
Все личные ответы используют `Cache-Control: no-store`. Пагинация и ограничения
коллекций определяются в OpenAPI до реализации UI.

Первый предлагаемый сценарий — рабочий день преподавателя: в SVG показаны группы,
ученики, создание занятия и контакт с родителями. Это предложение для первой роли,
а не выдача прав всем Core members. Шесть действий из SVG требуют следующих
контрактов; названия и пути здесь также предложены, а не реализованы:

| Действие SVG | Предлагаемый UI route | Необходимый backend workflow |
| --- | --- | --- |
| К текущему занятию | `/lessons/:id` | Доступное текущее занятие; его отсутствие показывается явно, без выдуманного ID |
| Создать занятие | `/lessons/new` | Создание занятия, выбор реальной группы, проверка времени и permissions |
| Создать группу | `/groups/new` | Создание группы в разрешённой организации и управление её участниками |
| Добавить ученика | `/students/new` | Учебная связь с Person, ограниченный поиск и проверка прав; создание нового Person только через Core application use case |
| Загрузить материалы | `/materials/upload` | Проверяемая загрузка файла, собственные метаданные Education, защищённая выдача файла |
| Написать сообщение | `/messages/new` | Реальный список допустимых адресатов, отправка и история; отдельное решение о владельце переписки |

`/calendar`, `/people`, `/messages`, `/more` также требуют реальных собственных
workflows и API. Файловый adapter и владельца переписки нужно определить до принятия
полного контракта; нельзя молча считать существующие email/outbox или профильные
административные endpoints их заменой. Наличие ссылки в SVG не означает наличие функции.
Произвольные URL от сервера не исполняются: переходы собираются из известных типов
действий и проверенных resource IDs.

## Порядок реализации после решения

1. Подтвердить полный зелёный Platform CI для базового SHA, включая оба browser jobs.
2. Принять или скорректировать это решение: runtime, схема, identity, первая роль
   пользователя, владельцы материалов/avatar и переписки, состав быстрых действий.
3. Создать Education OpenAPI и модель данных с write workflows. Реальные данные
   появляются через авторизованные операции создания/изменения, а не production seeds.
4. Реализовать backend, миграции, permissions и изолированные integration tests:
   другой пользователь/организация, отключённый модуль, empty day, сортировка,
   timezone/DST, материалы, privacy lifecycle и отсутствие доступа у Commercial identity.
5. Подключать frontend только к реализованным endpoints. Полный экран «Сегодня»
   открывается после готовности всех обязательных действий и пяти пунктов навигации.
   Test fixtures допустимы только внутри изолированных тестов.
6. Проверить RU/EN, light/dark, 393×852 и 1440 wide. Канонический светлый SVG:
   [мобайл.svg](../../apps/frontend/design/мобайл.svg). Сравнение проверяет контент,
   локальные Inter, палитру, радиусы, active state, 72px navigation и safe-area.

Фактический статус CI и локальной проверки подготовки находится в
[актуальном аудите](../AUDIT.md). Наличие этого документа не заменяет ни зелёный CI,
ни принятое backend-решение.
