# Data subject requests and processing blocks (Phase 4.1 B1)

Migration 022 adds four Core tables: `data_subject_requests`, `data_subject_request_deadlines`, `data_subject_request_events`, and `privacy_processing_blocks`. A request stores the subject Person separately from the submitting Person and Account. A self request derives both IDs from the authenticated human Account. A representative request requires a verified, currently valid `legal_representations` record with the request type's specific submission scope. The server checks the Account to Person link. Representative read access additionally requires the active `privacy.request.view` scope; revocation removes that access to old requests. Management uses `core.privacy.requests.read` and `core.privacy.requests.manage`.

Request types are `access`, `processing_information`, `correction`, `restriction`, `processing_termination`, `erasure`, `export`, and `consent_withdrawal`. `DataSubjectRequestTypeRegistry` holds their authority scope, deadline, completion capability, and block applicability. `DataSubjectRequestStateMachine` enforces submitted, identity verification, review, work, and terminal transitions. Events record only machine codes, actor Account ID, and time. Ordinary updates and deletion of events are blocked in PostgreSQL.

The deadlines table keeps the trigger, calendar type, original due time, optional one-time extension, and satisfaction time separately. The original trigger and due time are immutable. `PrivacyDeadlinePolicy` defines access/information and processing termination as 10 working days with at most 5 additional working days; confirmed correction as 7 working days; unlawful processing stop as 3 working days; and unlawful data destruction as 10 working days. The latter rules are available for a future explicit trigger and are not started by request submission. Calendar days and hours are separate calculation types. Overdue state is computed from the effective due time and satisfaction time.

`ConfiguredBusinessCalendar` accepts covered dates, weekend weekdays, additional non-working dates, and working weekend overrides. A working-day calculation outside coverage fails closed. Production defaults cover only 1970-01-01, so deployment must provide a verified calendar before accepting requests with working-day deadlines. Configure `PRIVACY_CALENDAR_COVERAGE_FROM`, `PRIVACY_CALENDAR_COVERAGE_UNTIL`, `PRIVACY_CALENDAR_NON_WORKING_DATES`, and `PRIVACY_CALENDAR_WORKING_OVERRIDE_DATES` for the relevant jurisdiction and period. The test environment has a small deterministic calendar and is not a legal calendar.

Processing blocks use subject, purpose, or semantic resource scope. Their service validates subject, configured purpose, source request ownership, and time ordering. Repeated creation of an active logical block returns its ID. Release is idempotent; expiration is computed using the shared `ClockInterface`. `ProcessingBlockPolicy` exposes a read-side `isBlocked` check to future modules. These blocks do not disable Accounts or archive Persons, and no access or export request automatically creates one.

The API provides self submission/list/get, representative submission, management list/get/transition/extension, and management block create/list/release. Mutations are transactional with audit records. Audit payloads are limited to typed machine codes and resource IDs. Inputs accept only documented fields; no free-text request body, operator note, or evidence document is stored. No DELETE endpoint exists.

The B1 workflow cannot claim execution of export, correction, erasure, restriction, processing termination, or consent withdrawal. Completion remains blocked for every request type until an actual execution or response capability and its evidence are implemented. Consent withdrawal must eventually call the existing canonical `ConsentService`. B2 adds export and correction/restriction contributors; B3 adds retention/legal hold; B4 adds erasure. Privacy incidents and deployment-specific legal controls remain outside B1.
