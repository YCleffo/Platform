# Хранение, ограничения обработки и уничтожение

Оценка хранения определяет допустимость действия; исполнитель уничтожения исполняет его после повторной проверки. Предыдущее `eligible_delete` не является постоянным разрешением на последующее удаление.

## Политики и кандидаты

`RetentionCandidateContributor` перечисляет ресурсы субъекта и все применимые цели. Кандидат содержит ID ресурса/субъекта, коды целей и политик, событие начала отсчёта и время. Поставщик выгрузки не заменяет источник кандидатов хранения.

Политика задаёт действие и явную единицу `calendar_days`, `working_days`, `hours` или `event_only`. Отсутствие нужной продолжительности или события начала отсчёта делает политику неполной. Промышленные сроки не выводятся из тестовых значений.

`RetentionEvaluator` проверяет цель, политику, событие отсчёта, срок, запрет уничтожения, основание, зависимости и действие. Согласие разрешается по текущему свидетельству без признака прежней записи; иные основания требуют поставщика актуальных доказательств. Неизвестное состояние блокирует уничтожение. Если хотя бы одна применимая цель требует хранения, физический ресурс сохраняется.

`RetentionDecisionService` сериализует оценку по ресурсу и пишет минимальную неизменяемую запись. `privacy/retention/evaluate --limit=100` выводит только счётчики и не удаляет данные.

## Блокировки обработки и запреты уничтожения

`privacy_processing_blocks` ограничивает обработку по субъекту, цели или семантическому ресурсу. `privacy_legal_holds` отдельно запрещает уничтожение. Создание активного логического ограничения или запрета уничтожения идемпотентно; снятие повторяемо. Сроки проверяются через общий `ClockInterface`.

Блокировка проверяется в доменных путях контактов, настроек и организаций. Поставщик сведений не хранит параллельную копию состояния. Отключение Account, архивирование Person и отзыв согласия сами по себе не являются уничтожением.

## Прекращение обработки

`POST /api/core/privacy/requests/{id}/processing-termination/execute` принимает запрос `in_progress`. Сервис собирает цели, оценивает основания и создаёт блокировки по цели там, где обработку можно прекратить. Исполнители ограничений должны повторяемо применять ограничение по ID блока.

Действующее основание фиксируется как сохраняемая цель и может дать частичный результат. Неизвестное основание, отсутствующий поставщик сведений или его техническая ошибка оставляют запрос открытым. Сервис не удаляет данные и не подменяет проверку исполнения сменой статуса.

## Планирование уничтожения

Дело принадлежит Person и может быть связано с запросом субъекта. Планирование собирает ресурсы по всем зарегистрированным целям и создаёт один элемент на физический ресурс. Отсутствие кандидатов, неполное покрытие целей или более 1000 кандидатов блокируют планирование. Элементы хранят ID и коды, а не копии удаляемых значений.

Изменение набора кандидатов после планирования даёт `candidate_set_changed`. Заблокированные и неподдерживаемые ресурсы остаются видимыми; они не исчезают из результата ради успешного статуса.

## Исполнение и обработчики

Рекомендательная блокировка дела сериализует исполнителей. Обработка ограничена порциями до 100 элементов. Для каждого элемента транзакция блокирует субъекта и дело, заново собирает цели, проверяет политику, основания, запреты уничтожения, зависимости, владение и соответствие действия обработчику.

Core поддерживает `delete` для собственных контактов, настроек аккаунта и членств организаций при допустимой политике. Активное членство блокирует действие. Для Person и человеческого Account поддерживается `anonymize`: операционные идентификаторы и учётные данные уничтожаются, UUID остаётся нейтральной опорой внешних ключей. Сервисный и системный Account в этот путь не входит.

Порядок обработки: дочерние контакты, настройки, членства, человеческий Account, затем Person. Обработчик Person отказывается работать при оставшихся контактах, членствах или активных связанных аккаунтах. Повтор уже выполненного обезличивания распознаёт нейтральную запись и не создаёт второй эффект. Обычные API не восстанавливают обезличенную учётную запись.

Общего разрушительного обработчика для согласий, представительства, запросов субъекта и юридических свидетельств нет. `delete`, `anonymize`, `pseudonymize` различаются; обработчик не может произвольно подменить действие.

Физическое изменение Core, аудит, свидетельство уничтожения и завершение элемента атомарны. Ошибка откатывает изменение и оставляет элемент доступным для повтора. Внешний модуль обязан согласовать внешние действия за пределами этой транзакции по ID элемента.

### Рабочая область Education

`education.workspace` — один принадлежащий субъекту ресурс с ID субъекта. Поставщик сведений выдаёт кандидата на каждую настроенную цель категории `education`; основание помимо согласия
определяется по активному аккаунту или членству Core, а неизвестное состояние сохраняет
данные. Ограничение по цели объявляет покрытие, но основная блокировка остаётся в
Core; юридические запреты уничтожения проверяются до обработчика.

Обработчик `education.workspace_erasure` удаляет метаданные Education в порядке зависимостей внешних ключей,
удаляет байты только принадлежащих субъекту файлов, отвязывает чужие файлы от удаляемых занятий и
пишет `education.privacy_receipts(item_id, result)` последним. Подтверждение находится в БД
модуля; байты файлов — вне транзакции Core, поэтому повтор после частичного отказа
обязателен. Повтор с тем же ID элемента распознаётся по подтверждению; новый ID элемента после успешного
удаления идемпотентно фиксирует завершение. [покрытие Education](../education-database-coverage.md).

## Результат и свидетельства

Свидетельство уничтожения содержит ID, машинные коды, HMAC-ссылку на ресурс, действие, время, исполнителя и срок хранения. Значения уничтоженных полей в него не копируются. Политика доказательств настраивается отдельно; код отклоняет срок короче трёх лет.

Техническая ошибка не закрывает срок запроса субъекта. Неуспешные элементы остаются повторяемыми; частичный результат фиксирует явные ограничения и основания. Завершение запроса требует свидетельств исполнения, а не только смены статуса дела. Технический экспорт свидетельств не заменяет подписанный организационный акт.

`privacy/cleanup` по отдельным политикам обрабатывает ограниченные категории: аудит, исходящую/входящую очереди, историю запросов, истёкшие ограничения/запреты, решения хранения, старые сессии и свидетельства уничтожения. По умолчанию используется проверка без удаления. Активные запреты уничтожения и неутверждённые категории сохраняются. Финансовая история в общую очистку не включена.

## Резервные копии и доступ

Удаление в основной БД не удаляет старые неизменяемые резервные копии немедленно. Перед обслуживанием восстановленной копии необходимо сверить журнал уничтожений и повторить уничтожение данных, удалённых после создания копии. Если это невозможно, восстановленная система остаётся изолированной.

Консольное уничтожение требует явного дела, исполнителя и полномочий. Прикладная роль БД и доступ к командам жизненного цикла должны быть ограничены отдельно; наличие контролируемой настройки сессии не делает суперпользователя безопасной промышленной ролью.
