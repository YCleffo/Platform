# Generic legal representation

`core.legal_representations` links a subject Person to a different representative Person, with a semantic authority type, validity range, verifier, evidence reference/hash, and immutable lifecycle evidence. It does not encode parent/student roles or store document scans. Storage can later attach protected evidence through a reference without becoming a Core dependency.

A declaration is not authority to grant consent. Migration 021 stores explicit action scopes in `core.legal_representation_scopes`. A manager supplies a nonempty set of registered scopes while declaring an authority. `LegalRepresentationService::verify` requires separate `core.privacy.representations.manage` permission (or the existing superadmin bypass), evidence type plus a reference/hash, a nonempty scope set, and an active validity interval. Scopes cannot be added to or removed from verified authority; a changed scope set needs a new authority record. Existing verified records without scopes remain evidence but authorize no action.

`RepresentativeAuthorityPolicy::assertActiveForAction` locks and checks an exact subject/actor pair, verified status, validity dates, absence of revocation, and the required action scope. Consent grant uses `privacy.consent.grant`; withdrawal uses `privacy.consent.withdraw`. The authority check and protected action share a transaction. Verification and revocation are idempotent. Revoked, expired, and rejected rows cannot be silently reactivated. Database CHECK/FK/trigger rules repeat durable invariants, including the consent insert gate.

Management endpoints under `/api/core/privacy/representations` require authentication and `core.privacy.representations.manage`. They declare, verify, and revoke authority; they do not grant consent. There is no public endpoint accepting an arbitrary Person ID to grant representative consent. Future domain modules must authenticate the actor and apply scoped relationship/access policy before invoking the internal service.
