# Personal data correction (Phase 4.1 B2)

Management first moves a correction request to `in_progress`, then calls `POST /api/core/privacy/requests/{id}/correction-evidence` with an empty body to confirm the correction evidence. This idempotently starts the `confirmed_correction` deadline from the shared application clock. `POST /api/core/privacy/requests/{id}/corrections` requires `core.privacy.requests.manage` and accepts `contributorCode`, `resourceId`, and a bounded `changes` object. The payload exists only in request memory.

`PersonalDataCorrectionContributor` owns validation and application for its resource type. The registry rejects duplicate codes and accepts future module contributors through DI. `core.person` accepts only `givenName`, `familyName`, `middleName`, `displayName`, and `birthDate`; it reuses Person input validation and `UpdatePerson`. `core.person_contact` accepts only `value`, `label`, and `isPrimary`; `UpdatePersonContact` uses the existing `ContactNormalizer`, checks subject ownership, clears contact verification when value changes, and handles primary contact semantics. Privacy never runs an independent Person update.

The orchestration transaction locks the request, checks type/state and confirmation, applies the domain update, records execution evidence, satisfies the correction deadline, completes the request, and writes request/audit events. A failure rolls back the domain change. Evidence and audit contain IDs, resource/contributor codes, changed field paths, and times, never previous or new values. A generic status transition cannot complete or reject the request without execution/response evidence. Correction does not create a new processing block or bypass a canonical block policy; Core correction is the legally directed update itself. Module contributors must decide how their own processing restrictions affect their update path.
