# Интернационализация Core и локализация API

## Область ответственности и направление зависимостей

Core Internationalization — единая среда выполнения для локализации API и системных
сообщений. Она отвечает за нормализацию локалей, правила поддерживаемых локалей,
определение локали запроса, неизменяемый контекст локали, перевод, заголовки ответа
и базовые каталоги сообщений. Communication использует ту же основу локализации,
но хранит шаблоны писем в отдельных ресурсах.

Необязательные и доменные модули могут определять собственные идентификаторы сообщений
или категории каталога, но используют среду Core Internationalization. Она не должна
зависеть от необязательных модулей. Education, Storage, Devices, Chat и Games не должны
создавать собственные средства определения локали или менять глобальную локаль переводчика.

## Контракт локали

Поддерживаемые значения локали — канонические теги BCP 47, заданные через
`SupportedLocales`. Текущая установка поддерживает `ru-RU` и `en-US`.
Устаревшие варианты `ru`, `ru_RU`, `en` и `en_US` нормализуются существующим
`LocaleNormalizer`; произвольные строки локали не считаются доверенными.

Локаль определяется отдельно для каждого запроса. Frontend передаёт явно выбранный язык единым
заголовком `X-Client-Locale`; query parameters для этого не используются.

1. Анонимный запрос: `X-Client-Locale`, затем `Accept-Language`, затем `APP_DEFAULT_LOCALE`.
2. Аутентифицированный запрос: `X-Client-Locale`, сохранённая пользовательская настройка
   `accounts.locale`, затем `Accept-Language`, затем `APP_DEFAULT_LOCALE`.

Ручной выбор сохраняется через `PATCH /api/auth/me/preferences`. Поэтому общая настройка браузера
не перебивает ранее сохранённый выбор аккаунта. Фактическая локаль при создании сессии записывается в
`auth_sessions.client_locale`; при последующих запросах авторитетным остаётся новый `ClientContext`.

Текущая policy семейства языков:

```text
ru, ru-RU, ru-KZ, ru-BY -> ru-RU
любой другой валидный язык -> en-US
нет пригодного языкового сигнала -> APP_DEFAULT_LOCALE (ru-RU)
```

Таким образом, `de-DE` или `fr-FR` являются иностранным языковым сигналом и получают английский,
а не default. GeoIP не участвует в выборе языка и может использоваться только для timezone/risk context.

Весовые значения `Accept-Language`, исходный порядок, резервный выбор по языку,
маски, некорректные значения и `q=0` централизованно обрабатывает `LocaleResolver`.
После аутентификации неизменяемый `ClientContext` запроса заменяется новым контекстом
с учётом локали аккаунта; общий переводчик никогда не изменяется глобально.

## Контракт HTTP-представления

Каждый локализованный ответ API содержит каноническую локаль:

```http
Content-Language: ru-RU
Vary: Accept-Language, X-Client-Locale
```

Существующие значения `Vary` сохраняются, а оба locale-заголовка добавляются один раз. Sensitive API
одновременно использует `Cache-Control: no-store`, поэтому ответы разных пользовательских контекстов
не попадают в shared cache.
Машиночитаемые данные не зависят от локали: коды статусов и сообщений, UUID, значения
enum, коды разрешений, временные метки, метаданные пагинации и пользовательский контент не переводятся.

Ошибки имеют единую структуру:

```json
{
  "error": {
    "code": "auth.invalid_credentials",
    "message": "Неверное имя пользователя или пароль.",
    "requestId": "..."
  }
}
```

Внутри `error` могут присутствовать `details`, `fields` и `meta`. Для валидации используется
`validation.failed` and groups field entries as `{code, message}`. The code and
JSON topology stay stable across locales; only human-readable messages vary.

На HTTP-границе предусмотрены соответствия с каталогом для кодов 400, 401, 403, 404, 405,
409, 413, 415, 422, 429, 500 и 503. Ответы фреймворка, например для некорректного JSON
или запрещённого метода, нормализуются там же. Необработанные исключения журналируются
с исходным объектом исключения, а клиент получает только локализованное `http.internal_error`;
классы исключений, трассировки, SQL, пути, секреты, токены и внутренние сообщения в ответ не попадают.

## Каталоги и идентификаторы сообщений

Базовые каталоги — массивы PHP по следующим путям:

```text
resources/messages/en-US/app.php
resources/messages/ru-RU/app.php
```

Идентификаторы сообщений семантические и стабильные (`http.*`, `validation.*`, `auth.*`,
`account.*`, `person.*`, `rbac.*`, `session.*`). Один идентификатор должен присутствовать
в обоих каталогах и соответствовать непустой строке UTF-8. Для чисел и динамических
значений используются параметры ICU через `IntlMessageFormatter`; локализованные предложения
не собираются конкатенацией.

В разработке и тестах отсутствующий перевод явно обозначается его идентификатором,
а тесты соответствия каталогов завершаются ошибкой. В production `TranslationService`
заменяет отсутствующий публичный перевод безопасным локализованным сообщением
`http.internal_error`.

## Граница домена и пользовательского контента

Исключения домена/приложения описывают семантические ошибки и не зависят от HTTP и локали.
Action сопоставляют типы исключений с семантическими идентификаторами сообщений и статусами;
они никогда не показывают клиенту `Throwable::getMessage()`. Только фабрика ответа
преобразует идентификатор сообщения в публичный текст.

Переводится только системный текст и текст интерфейса. Имена пользователей, метки,
контактные данные, произвольный текст, метаданные загруженных файлов, содержимое БД,
значения enum, коды ролей/разрешений и машинные поля передаются без изменений.

## Интеграция с аутентификацией

Аутентификация и авторизация используют одну фабрику ответа и контекст локали запроса.
Для неизвестного пользователя и неверного пароля всегда возвращаются одинаковые код
`auth.invalid_credentials` и текст, что не позволяет перебирать аккаунты.
Ошибки сессии, обновления токена, активации, сброса пароля, разрешений, ограничения частоты
запросов и доступности сервиса задаются идентификаторами каталога, а не строками в коде.

## Интеграция с электронной почтой

Communication получает канонические значения локали от Core Internationalization и
формирует письма из `resources/email/<locale>/...`. Темы, HTML и обычный текст письма
отделены от каталогов API, но используют общие нормализацию, набор поддерживаемых локалей
и policy языковых семейств. Переводы API не используются как шаблоны писем.

Язык transactional email определяется по origin context:

```text
interactive request -> current resolved ClientContext locale
background/system event -> saved accounts.locale -> APP_DEFAULT_LOCALE
admin invitation -> invited account locale -> APP_DEFAULT_LOCALE
```

Локаль инициатора-администратора не становится локалью приглашённого. Password reset, password changed,
activation self-service, external identity и MFA/security письма из активного HTTP-взаимодействия используют
локаль этого взаимодействия. `EmailService` записывает окончательное `ru-RU` или `en-US` непосредственно
в payload Communication Outbox. Worker не читает `accounts.locale` повторно: изменение preference после
создания события не меняет язык уже поставленного письма.

Для каждого production template обязательны `subject.txt`, `html` и `txt` одновременно в `ru-RU` и
`en-US`. Runtime не маскирует отсутствующий обязательный перевод silent fallback-ом.

## Автоматические проверки

Тесты проверяют наличие обязательных локалей, структуру каталогов, строки UTF-8,
совпадение ключей ru-RU/en-US, строгий parity трёх файлов каждого email template и покрытие всех
констант `ApiMessage`. Отдельные regression-сценарии проверяют языковые семейства, веса
`Accept-Language`, explicit header, приоритет сохранённой настройки, locale password-reset письма,
background fallback и неизменность locale в Outbox. Архитектурная
проверка запрещает устаревшие ответы `fail()`, `error_message`, исходный текст исключений,
строковые сообщения валидаторов и строковые тексты ошибок в коде API/HTTP-границы.
Ответы, исключения, локали, форматирование параметров, заголовки и поведение HTTP
для ru/en покрываются независимыми проверками.
