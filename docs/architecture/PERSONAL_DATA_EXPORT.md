# Personal data export

`GET /api/auth/me/privacy/requests/{id}/data` issues a subject's access or export response after the request reaches `in_progress`. The representative route is `GET /api/auth/me/privacy/representations/{representationId}/requests/{id}/data`. Both require a human Account linked to a Person. Self access requires the request subject to equal that Person. Representative access checks the request's representation ID, current verified validity, `privacy.request.view`, and `privacy.data.access` or `privacy.data.export` according to request type. Management read permission does not grant export.

`PersonalDataContributor` receives a narrow `PersonalDataExportContext` and returns a typed `PersonalDataSection`. The DI provider registers Core and Auth contributors; modules can supply more through `personalDataContributors`. Duplicate or invalid codes fail registry construction. Contributors run in code order and must return stable record order. The exporter canonicalizes object keys, stamps export schema version `1`, and calculates SHA-256 and byte count from the exact JSON body sent to the client. It rejects more than 32 sections, 1000 records per section, 1 MiB total, depth 8, or an 8192-byte string. The Core SQL contributors read at most 1001 rows per section so oversize results fail closed. A contributor failure fails the whole export.

Core exports subject Person, own contacts, human Account metadata, stored settings, own consent evidence, representations where the Person is subject, own request metadata/deadlines, and processing blocks. Auth exports an allowlist of identifier values and verification state, external provider link/display metadata, passkey/TOTP existence metadata, and session times/client metadata. Password hashes, MFA secrets, recovery hashes, passkey key material, session tokens/hashes, external claims, audit dumps, and outbox payloads are excluded. Account settings are stored overrides; effective defaults are governed by the settings registry.

The exporter builds the document while holding a database transaction and request row lock, then inserts execution evidence, satisfies the access deadline, and completes the request before returning the body. The transaction ends before the HTTP server sends bytes. `response_issued` describes server issuance; it does not claim the client received the full body. The execution table stores schema version, digest, size, actor and machine codes only. It never stores the response body. Responses use JSON, `Cache-Control: no-store`, and `X-Content-Type-Options: nosniff`. Large exports return a controlled 413 and leave failed execution evidence with no deadline satisfaction. Streaming or encrypted storage artifacts require a later design.
