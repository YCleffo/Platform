# Безопасность Commercial Control Plane

Commercial использует собственные `control_users`, сессии и членства. Core Account или `core.superadmin` доступа не дают.

## Учётные данные и сессии

Пароли хеширует Symfony PasswordHasher. Нормализованная почта уникальна; отображаемая версия хранится отдельно. Статусы: `pending_verification`, `active`, `suspended`, `disabled`.

Одноразовые подтверждения почты и сброса имеют срок и хранятся как хеши. Непрозрачные токены доступа краткоживущие; токен обновления меняется при каждом использовании. Повтор использованного токена отзывает семейство сессии. Выход идемпотентен; просроченные данные очищает контролируемая консольная команда.

Активность пользователя, отзыв и оба срока сессии проверяются на каждом запросе с токеном доступа. `last_used_at` приблизителен: первый вход пишет время, последующие запросы — не чаще раза в минуту. Обновление токена пишет сразу. Это снижает конкуренцию записи одной строки; авторизация и доказательства MFA не кэшируются.

Секрет TOTP шифруется отдельным ключом 32 байта. Подключение переходит из `pending` в `active` после проверки кода; повтор TOTP или использованного резервного кода запрещён. Сброс пароля отзывает сессии и проверочные данные по жизненному циклу.

Свежий TOTP или резервный код повышает парольную сессию до `password_totp`/`password_recovery` и атомарно записывает `mfa_authenticated_at`. Обновление токена сохраняет свидетельство, но не создаёт новую MFA-проверку.

## Авторизация и чувствительные действия

`AccountAuthorization` проверяет действующее членство и разрешение каждого ресурса аккаунта. UUID пути сам доступа не даёт. Роли Commercial: `owner`, `admin`, `billing`, `technical`. Понижение/удаление владельца блокирует аккаунт; отложенные ограничения запрещают отсутствие активного владельца.

Чувствительные действия расчётов, возвратов, подписок и сохранённых способов требуют недавнего первичного подтверждения и MFA. Внешней компенсации дополнительно нужны два разных отдельно уполномоченных финансовых оператора.

## HTTP и аудит

Регистрация, вход, повторная отправка, обновление токена и создание аккаунта ограничены истекающими счётчиками с HMAC-ключами. Тело API — до 64 КиБ. Ошибки не раскрывают SQL, трассировку, пути и секреты.

Используются Bearer-токены, не аутентификация cookie. CORS закрыт по умолчанию. Чувствительные ответы имеют `no-store, private`; защитные заголовки запрещают встраивание, распознавание типов по содержимому и ограничивают источник перехода. Аудит хранит ID цепочки, идентификаторы и разрешённые типизированные поля; пароли, исходные токены, Authorization и произвольные снимки исключены.

Уведомление YooKassa не доверяет JSON или перенаправленному IP как доказательству оплаты. Итог подтверждается серверным запросом провайдеру и локальным контрактом. Публичный маршрут ограничен по IP; в промышленной среде рекомендуются `CONTROL_YOOKASSA_WEBHOOK_IPS` со списком CIDR и корректные доверенные прокси, отсекающие посторонних до записи входящего события и запроса провайдеру.

## Конфигурация и выполнение

Промышленный запуск требует `CONTROL_APP_SECRET`, `CONTROL_TOKEN_SECRET`, корректный `CONTROL_TOTP_ENCRYPTION_KEY`; оплата — действующий HTTPS-адрес возврата и настройки продавца. Демонстрационные секреты не подставляются.

Промышленный образ работает как `www-data`, не имеет зависимостей разработки, `.env`, метаданных Git и тестов. Запись разрешена в рабочие каталоги. У приложений раздельные секреты БД и сети; HTTP Commercial не получает сокет Docker, Core — закрытый коммерческий ключ подписи.

`/health` ограниченно проверяет доступность; `/health/ready` дополнительно учитывает зависимости и обязательную активность. Успешный HTTP не доказывает минимальные права БД или промышленную отказоустойчивость.

## Приглашения

- Токен: 256-битный доменно-разделённый HMAC `i1.<id>.<version>.<mac>`; в БД только SHA-256. Повторная отправка меняет версию, старые ссылки перестают действовать. По умолчанию 7 дней: `CONTROL_INVITATION_TTL_SECONDS`.
- Ссылка `/invitation#token=…`: фрагмент обычного запроса не уходит серверу. Интерфейс держит токен в памяти, очищает через `history.replaceState`, не пишет в хранилища, строку запроса, аналитику или журналы; применяется `Referrer-Policy: no-referrer`.
- Предпросмотр не требует входа и не меняет данные. Принятие/отклонение требует входа, подтверждённой совпавшей нормализованной почты. Создание идемпотентно; создание/повторная отправка ограничены по частоте; создание, повторная отправка и отзыв требуют `requireSensitiveMfa`.
- Исходящая почта: цель `control_account_invitation`, категории `contact_email`, `invitation_link`, `organization_name`. Без решения оператора отправка отклоняется; готовность требует такого решения.
- Обход RBAC в `MembershipService::add()` закрыт: права проверяются после блокировки аккаунта с учётом текущей роли; смена через добавление даёт 409.
