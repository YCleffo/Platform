# FRONTEND_09 Closeout — память и навигация

На одинаковых HTTP-фикстурах после сборки мусора число DOM nodes и listeners оставалось постоянным в Core Admin и Commercial Account. Рост счётчиков без сборки мусора воспроизводится на обеих ревизиях. Ранее зарегистрированные 2495 мс в Commercial Account с реальным API в этом клиентском эксперименте не воспроизведены. Источник того выброса остаётся `NOT_VERIFIED`.

## Условия сравнения

- Baseline `4cf8c6d40ea107f6da1c3265c97a098962b78615` и кандидат `793d5d3616906fa9afeba2fd9f3dbe3dc0717e43` собраны в отдельных detached worktrees с общей версией frontend-зависимостей и `VITE_EDUCATION_ENABLED=0`. При сравнении с `1fde0341` файлы `apps/frontend/src`, `index.html` и `package-lock.json` идентичны кандидату.
- Использован один экземпляр headless Chrome 158.0.8127.37. Каждый прогон открывал новый контекст 1440×900, EN Light, reduced motion. Перехват всех HTTP-запросов разрешал статические ресурсы только с loopback-адреса соответствующего preview и обслуживал API из одних и тех же фикстур.
- Core Admin проходит Dashboard → Modules → Dashboard → Settings → Dashboard. Commercial Account проходит Overview → Invitations → Overview → Billing → Overview. Каждый прогон выполняет 12 переходов warm-up, затем 100 измеряемых кликов. URL, содержимое целевой страницы и активная ссылка проверяются после каждого клика.
- У каждого пространства есть отдельные прогоны с обычной сборкой мусора Chrome и с принудительной сборкой в контрольных точках 0, 30, 60 и 100. Все точки приходятся на один и тот же исходный экран. Перед замером проверяется готовность шрифтов и отсутствие запросов на протяжении двух кадров.
- Использованы `Performance.getMetrics` для used heap, `Memory.getDOMCounters` для DOM nodes и JS listeners, `DOMDebugger.getEventListeners` для точных обработчиков `window` и `document`. Диагностическая сборка мусора вызывает `HeapProfiler.collectGarbage`. Long tasks регистрирует `PerformanceObserver`. Задержка измеряется от начала клика до ожидаемого URL, содержимого и активной ссылки, включая работу Playwright и браузера. [Chrome DevTools Protocol](https://chromedevtools.github.io/devtools-protocol/)

## Интерпретация

В обеих ревизиях при работе Chrome без принудительного GC временно накапливаются документы, ноды и связанные обработчики. Стабилизация DOM, listeners и документов после GC подтверждает, что эти объекты освобождаются в пределах проверенного цикла. JS heap отдельно немного растёт в обеих ревизиях. По этим счётчикам типы оставшихся JS-объектов нельзя определить. Результат не устанавливает причину роста heap и не исключает утечки вне протестированных маршрутов.

У кандидата обоих кабинетов на один глобальный обработчик `storage` больше. Он регистрируется в `initLocale` один раз на документ для синхронизации языка между вкладками. На каждой контрольной точке набор обработчиков `window` и `document` оставался одинаковым внутри одной ревизии. Остальные различия в абсолютном числе обработчиков относятся к разным версиям и их исходному DOM.

Проверка путей очистки подтвердила, что `AdminLayout` снимает обработчик изменения viewport и временные pointer/keyboard handlers. Observer прокрутки в `AccountLayout` отключается в cleanup watcher. `AppMenu` отключает `ResizeObserver`, отменяет кадр и снимает scroll, keydown и pointerdown handlers. `AppBottomNav` снимает window listeners и отключает observer в unmount. Billing и Invitations проверяют актуальность асинхронного результата по поколению загрузки или токену запроса и epoch сессии. Heap retainers отдельных observers, watchers и таймеров не снимались.

Данные не показывают накопления живых узлов или обработчиков, требующего изменения production-кода. Медленный переход Commercial с реальным API стоит перепроверить с отдельными метками начала fetch, HTTP-ответа, отрисовки и ожидания Playwright. Это поможет отличить вклад сервера и сети от задержки клиентского интерфейса.

## Повтор запуска

Создать чистые checkout указанных SHA и собрать обоих `node node_modules/vite/bin/vite.js build` с одинаковой конфигурацией. Запустить локальные preview на 4216 и 4217, настроив Core и Commercial proxy на `http://127.0.0.1:1`. В `apps/frontend` текущего рабочего дерева выполнить:

```powershell
$env:PERF_BASELINE_URL = 'http://127.0.0.1:4216'
$env:PERF_CANDIDATE_URL = 'http://127.0.0.1:4217'
$env:PERF_BASELINE_SHA = '4cf8c6d40ea107f6da1c3265c97a098962b78615'
$env:PERF_CANDIDATE_SHA = '793d5d3616906fa9afeba2fd9f3dbe3dc0717e43'
node scripts/verify-frontend09-navigation-performance.mjs
```
