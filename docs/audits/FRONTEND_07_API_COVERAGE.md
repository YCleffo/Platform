Из зарегистрированных операций 362 имеют OpenAPI-описание, 398 связаны с frontend-клиентом, а 377 имеют потребителя в маршрутизируемом интерфейсе. Статический снимок воспроизводится командой `node apps/frontend/scripts/frontend07-coverage.mjs --check` из корня репозитория с установленными Composer-зависимостями Core и Commercial. Поля `contracts`, `frontendApi`, `ui` и `permission` дают ссылки на реализации. В `undocumentedCore` перечислены все 85 Core-операций без OpenAPI, включая категорию, исходный маршрут, действие и требования к доступу. [Машинный реестр](frontend07-coverage.json)

Среди 85 Core-операций есть 13 публичных, 11 пользовательских, 53 административных и 8 служебных. Зарегистрированных устаревших операций в этом списке нет. Для `INTERNAL` отмечены требования к регистрации Agent, служебной подписи, провайдерским событиям или изолированному тестовому рантайму. У проб готовности и идентификации сервиса указан отдельный статус проверки входного трафика на развёртывании.

## Проверка браузерного результата

Запуск `--run-evidence` принимает только зарегистрированные браузерные сценарии и сначала проверяет доказательство изоляции напрямую у Core и через frontend proxy. Манифест связывает результат процесса, идентификатор прогона, точный Git HEAD, SHA-256 содержимого исходников, отметку о рабочем дереве, время прогона и отпечаток доказательства изоляции. Сырые токены и подписанные URL в манифест не входят. `--check-evidence` требует свежие успешные результаты всех трёх сценариев и проверяет хеш артефакта каждого результата. Можно передать несколько манифестов из одного изолированного окружения, если каждый сценарий встречается один раз. Для отдельного снимка с результатами используется `--evidence <manifest>... --output <snapshot>`.

Связь с браузерным сценарием задаётся по конкретным операциям. Преподаватель доказывает создание ученика, сохранение результата и отображение в журнале. Classroom доказывает чтение состояния, назначение, завершение и восстановление через команды оператора. Storage доказывает доступ к списку, восстановление версии и подтверждение передачи. Родственные методы сохраняют свой статический статус. Исторические результаты FRONTEND_06 остаются доступными в исходном отчёте. [Генератор](../../apps/frontend/scripts/frontend07-coverage.mjs)

Проверенный локальный снимок содержит 12 `FULL`, по 4 в Education, DeviceManagement и Storage. Для 2 операций Storage зафиксирован `ALTERNATIVE_VERIFIED`. В этом снимке 386 операций имеют статус `PARTIAL`, 8 имеют `NOT_UI_REQUIRED`, 39 имеют `INTERNAL`. Манифесты содержат точный HEAD с отпечатком рабочего дерева. [Education](evidence/frontend07/teacher/manifest.json) · [DeviceManagement](evidence/frontend07/classroom/manifest.json) · [Storage](evidence/frontend07/storage/manifest.json)

У десяти прежних `MISSING` есть альтернативный пользовательский маршрут. Каждый из них имеет указание на основной endpoint и причину в JSON. Статический статус `NOT_UI_REQUIRED` означает, что отдельный интерфейс для этого варианта не нужен. Статус `ALTERNATIVE_VERIFIED` появляется только при наличии валидного доказательства для основного маршрута.

## Приоритеты оставшейся приёмки

Размер `S` означает сценарий в одном существующем разделе, `M` связывает несколько разделов или ролей, `L` требует отдельного системного стенда или независимого провайдера.

| Приоритет и размер | Плоскость и существующий UI | Сценарий и риск | Пробел и следующее изменение | Условие приёмки |
| --- | --- | --- | --- | --- |
| P0 · M | Core Identity, Auth, Security — `/admin/profile`, `/login`, `/admin/security` | Восстановление входа, MFA, отзыв сессии. Риск повторного доступа отозванной сессии | Свежие сценарии под текущий SHA для существующих форм и списка сессий | Повторный вход, перечитывание состояния и отказ отозванному токену |
| P1 · M | Core Admin и Privacy — `/admin/rbac`, `/admin/organizations`, `/admin/privacy`, `/admin/profile/privacy` | Назначение прав и приватный запрос. Риск выхода за границу организации | Контракты внешних административных операций по реестру и проверки с минимальными правами | Route parity, read-back запроса или назначения, запрещённый доступ в другой организации |
| P1 · M | Commercial Accounts и Members — `/accounts/:accountId`, `/accounts/:accountId/members` | Управление участником и приглашением. Риск изменения чужого аккаунта | Свежий браузерный тест приглашения, изменения роли и отзыва в действующих формах | Сохранённые роли после повторного чтения и отказ вне аккаунта |

Риск повторного списания | CI-доказательство по действующим сценариям с изолированным Control Plane и тестовым биллингом | Один финансовый результат после повторной доставки и сверка со стороны клиента и оператора |

В JSON приоритет указан для каждой операции. Для отсутствующих Core-контрактов сначала документируются внешние действия по безопасности и доступу, затем пользовательские настройки и эксплуатационные действия. Внутренние обработчики классифицируются отдельно с указанием их назначения и контекста доступа.

Первый пакет контрактов Core включает `GET /api/auth/sessions`, `DELETE /api/auth/sessions/{id}` и `POST /api/auth/sessions/revoke-others`. Для него нужны модель сессии, авторизация владельца, семантика отзыва и сценарий повторного чтения списка. Второй пакет включает операции с представительством и legal hold из `undocumentedCore`. Для него нужны контекст доступа администратора и ограничения переходов. Каждый пакет должен сверять метод и путь с зарегистрированными маршрутами и проверять фактические ответы на успешную операцию и отказ.
